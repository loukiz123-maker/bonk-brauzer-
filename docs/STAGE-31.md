# Этап 31: строгий режим (`"use strict"`)

Этап 30 закончился на 8 835 пройденных файлах test262 при 17 538 в конверте
(50.4 %). Самый большой кластер провалов после него — strict-режим: 593 файла с
вердиктом «ожидалась ошибка разбора, получили ошибку рантайма» и 702 «ожидалось
исключение». Причина одна: `"use strict"` в движке не значил ничего, поэтому
код, который стандарт объявляет ранней ошибкой (`with`, `delete x`,
восьмеричный литерал, `eval` как имя), спокойно исполнялся, а строгие правила
присваивания не соблюдались.

Этап добавляет строгий режим целиком: директиву, ранние ошибки разбора и
рантайм-семантику. По дороге нашлась целая пачка дефектов парсера, которые
strict-тесты обнажили (числовые литералы перед `.`, сокращённые методы в
объектных литералах, вычисляемые ключи, `new new X()`), — они тоже здесь.

## Что сделано

### 1. Директива `"use strict"` (пролог директив)

`note_directive` собирает пролог: строка-литерал в начале программы или тела
функции считается директивой, пока не встретился настоящий оператор. Строгий
режим записывается в AST (`StmtNode::is_strict` для программы,
`FunctionNode::is_strict` для функции), а не в глобальный флаг парсера — иначе
он «протекал» бы в соседние функции.

* строгость **наследуется** вложенными функциями (`outer(){ "use strict";
  inner(){} }` — `inner` тоже строгая);
* после тела функции состояние **восстанавливается** (`function f(){"use
  strict";} with(o){}` в sloppy-скрипте остаётся sloppy);
* `parse_block(bool function_body)` включает позицию директивы только для тела
  функции; обычный блок директив не содержит.

### 2. Ранние ошибки разбора

В строгом коде теперь `SyntaxError` для:

* `with (...)` — сообщение `'with' is not allowed in strict mode`;
* `delete` неприквалифицированного идентификатора;
* восьмеричных литералов (`010`) и восьмеричных escape-последовательностей
  (`'\1'`) — лексер помечает их флагами `Token::octal_literal` /
  `Token::octal_escape`, а решает парсер (в sloppy это по-прежнему допустимо);
* `eval`/`arguments` как имени переменной, параметра, `catch`-параметра, имени
  функции, цели присваивания (в том числе `+=`, `++`, `--`);
* зарезервированных в strict слов (`let`, `static`, `yield`, `implements`,
  `interface`, `package`, `private`, `protected`, `public`) — как имён;
* повторяющихся параметров: в strict для простого списка (`function f(a, a)`) и
  **всегда** для непустого простого списка (`function f(a, a = 1)`,
  `function f([a], [a])`, `function f(a, ...a)`) — ES2015 14.1.2;
* getter-а с параметрами и setter-а без ровно одного параметра (объектные
  литералы и классы).

В sloppy-коде `let`, `static`, `yield` теперь наоборот **можно** использовать как
имена (`var let = 1`, `f(static, yield)`), чего движок раньше не умел: лексер
помечает их как ключевые слова, а `is_identifier()` учитывает режим.

### 3. Тела классов — всегда строгие

`class A { m() { with (o) {} } }` — `SyntaxError` независимо от режима внешнего
кода: тело класса по стандарту является strict-кодом. Строгость ставится в
`parse_class` вокруг списка методов (наследуемое выражение `extends` при этом
остаётся обычным кодом).

### 4. Рантайм-семантика

Строгость доезжает от AST до места исполнения:
`Function::is_strict` → `Scope::is_strict` → `strict_scope(scope)`.

* запись в необъявленное имя — `ReferenceError` (в sloppy создаётся глобальная
  переменная);
* запись в неперезаписываемое свойство, в нерасширяемый объект, в `length`
  массива — `TypeError` (в sloppy молча игнорируется);
* `this` в strict-функции, вызванной без получателя, — `undefined`;
* `arguments` в strict-функции — **несвязанный** объект: `a = 2` не меняет
  `arguments[0]` (в sloppy — связанный, как и раньше).

Плюс два «соседних» исправления, без которых strict-семантика не сходилась:

* `this` в глобальном коде теперь равен `globalThis` (10.2.1.2), а sloppy-функция,
  вызванная без получателя, получает глобальный объект (10.4.3.1) — раньше
  везде был `undefined`;
* `Context::evaluate` выставляет строгость глобальной области на время прогона и
  восстанавливает её (без этого проверки рантайма не срабатывали никогда —
  первая версия «молча» пропускала `ReferenceError`).

### 5. Найденные по дороге баги парсера

Все они всплыли на strict-тестах и валят целые кластеры:

| дефект | следствие | исправление |
|---|---|---|
| число жадно съедало вторую точку | `1.5.toString()`, `0..toString()` — `SyntaxError` | одна точка на литерал; `.` после экспоненты (`1e3.toString()`) — доступ к свойству |
| число перед идентификатором | `1.toString` разбирался как `1.` + `toString` | лексер даёт `SyntaxError` «numeric literal must not be followed by an identifier» |
| `010` считался десятичным | в sloppy `010 === 10` | octal-разбор (`010 === 8`), `08`/`09` остаются десятичными |
| нет сокращённых методов | `{m() {…}}`, `{'n'() {…}}`, `{3() {…}}` не парсились | метод-литерал = функция с именем ключа |
| нет вычисляемых ключей | `{[k]: v}`, `{[k](){}}`, `{get [k](){}}`, `class A { [k](){} }` | `PropertyDef::computed_key` / `ClassMethod::computed_key`; ключ вычисляется один раз до значения и до установки методов |
| нет вычисляемых ключей в паттернах | `var {[k]: v} = o` | ключ сворачивается в вычисляемый доступ к элементу при десугаривании |
| числовой ключ у аксессора | `{get 0(){}}` не парсился | числовой литерал разрешён как имя свойства |
| `new new X()` | `SyntaxError` вместо `TypeError` в рантайме | `new` как callee `new` |
| `try` без `catch`/`finally` затирал чужую ошибку | «try without catch or finally» вместо настоящей причины | сообщение ставится только если ошибки ещё нет |
| `catch ({message})` | не поддерживался паттерн в `catch` | паттерн распаковывается в начало блока через `__bonk$catch*` |

## Открытые пункты (следующий этап)

Нынешняя картина провалов (8 074 файла), сгруппированная по причине:

| причина | файлов | что это |
|---|---|---|
| `Test262Error` (неверный результат) | 4 474 | семантика встроенных объектов: дескрипторы, `Array`-методы, `String` |
| `ReferenceError` на неизвестное имя | 1 250 | `Symbol` (204), `Date` (150), `Proxy`, `Map`/`Set`, `Promise`, `RegExp` |
| `TypeError` | 897 | нет валидации аргументов/дескрипторов в `Object`, `Array` |
| `unexpected character '\'` | 324 | regex-литералы и `\uXXXX` в идентификаторах |
| `with` в sloppy-коде | 234 | `with` не реализован вовсе (в strict — уже правильная ошибка) |
| `import`/`export` | 207 | модули вне конверта по признаку, но часть файлов без флага `module` |
| regex-литерал (`unexpected token '/'`) | 105 | то же, что и `\` — нет `RegExp` |
| прочие `js.syntax` | ~400 | `async`, генераторы (`function*`), метки операторов, `switch` |

Кластеры, которые дадут больше всего за этап:

* **`RegExp`** (литералы + `String.prototype.match/replace/split/search`):
  693 файла `built-ins/String` висят на нём почти целиком.
* **`with` в sloppy** (234) — самая дешёвая крупная позиция: объектное окружение
  имени поверх цепочки областей.
* **`Symbol` + итераторы** (204 + `Array.from`/`keys/values/entries`): без него
  не сдвинутся `Array`/`String` итераторы и spread по итераблам.
* **`Date`** (150) — отдельный, хорошо изолированный объект.
* **метки операторов** (`label:`, `break label`): 53 файла с `expected ';' but
  found ':'` — при этом `break`/`continue` с меткой уже разбираются.
* **полная валидация дескрипторов** в `Object.defineProperty`/`defineProperties`
  (1 540 файлов `built-ins/Object`).
