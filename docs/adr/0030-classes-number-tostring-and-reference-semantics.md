# ADR 0030: классы поверх существующей модели функций, `ToString` чисел и ссылочная семантика чтения

Дата: 2026-11-05. Этап: 28.

## Контекст

К концу этапа 27 движок имел: функции-замыкания (`Function` + `Scope`),
неявные прототипы (`Object.prototype`, `Array.prototype`, прототипы примитивов
в `RuntimeState`), собственные свойства функций и массивов, аксессоры двух
видов (`getters`/`setters` без получателя и `receiver_getters`/
`receiver_setters` с ним). Ни классов, ни `Function`, ни `__proto__` не было.

Одновременно полный прогон test262 показал три «дешёвых» кластера падений:
формат чисел (`1e-06` вместо `0.000001`), примитивный получатель в
`Array.prototype.*` и чтение неразрешённой ссылки (возвращало `undefined`
вместо `ReferenceError`).

## Решение

### 1. Классы — надстройка, а не новый вид значения

`class` не вводит `ValueType`: конструктор класса — обычная `Function`
(либо обёртка над AST-функцией `constructor`, либо нативная лямбда для
синтезированного и пустого конструктора), а «классовость» выражается тремя
фактами:

* `prototype_object` содержит методы как неперечисляемые свойства;
* `statics` содержит статические методы, а при `extends` — ещё и
  `prototype = statics родителя` (статическое наследование через ту же цепочку,
  которой пользуется `get_member` для функций);
* `prototype_object->prototype = родительский prototype_object`, поэтому
  `instanceof` работает без изменений.

`super` не заводит `[[HomeObject]]`: у функции есть `Function::super_function`
(`weak_ptr`), а при вызове в область видимости кладётся переменная `super`.
`super(...)` вызывает родителя с текущим `this` (`lookup_this` ищет ближайшую
функциональную область), `super.m(...)` ищет `m` в `super.prototype_object`,
начиная с `receiver_getters`, чтобы `this` внутри метода был правильным.

Отвергнуто: отдельные `ValueType::Class`/`Object::Kind::Class`. Пришлось бы
дублировать весь код вызова, `new`, `instanceof` и `Function.prototype.*`;
выигрыш — только в `typeof` (он и так `"function"`) и в проверках вида
`C.prototype.constructor`.

Отвергнуто: хранить `[[HomeObject]]` в `Function` и реализовывать `super`
через него. Для нашей модели (методы всегда создаются в `make_class`) хватает
ссылки на родительский конструктор; `HomeObject` понадобится только для
`super` в объектных литералах.

### 2. `ToString(Number)` — алгоритм стандарта, а не `%g`

Кратчайшая обратная запись ищется перебором `%.1g…%.17g` (round-trip
проверяется `strtod`), затем строка нормализуется: обычная запись при
`1e-6 ≤ |x| < 1e21`, иначе экспоненциальная без паддинга (`1e-7`, `1e+21`).
Функция используется и для `String(x)`, и для `to_property_key`, поэтому
исправление автоматически починило ключи свойств.

Отвергнуто: `std::to_chars` (C++17, shortest round-trip). Она даёт
`1e-07`/`1e+21` в формате, отличном от ECMAScript, и её пришлось бы
постобрабатывать всё равно; плюс библиотека зависимостей от локали не
добавляется.

### 3. Чтение неразрешённой ссылки — `ReferenceError`

`eval(Identifier)` бросает `ReferenceError`, если имя не найдено ни в одной
области. Освобождены ровно три контекста, где ссылка не читается: `typeof`
(проверяет наличие имени до вычисления), `delete` (обрабатывается до `eval`) и
цель простого присваивания/`for-in` (создаёт глобальное свойство в sloppy-коде).

Отвергнуто: различать sloppy/strict. Strict-режима в движке нет; в sloppy
чтение необъявленной переменной всё равно `ReferenceError`, разница только в
записи.

### 4. `length_hint` вместо `resize`

`length` массива — это `max(elements.size(), length_hint)`; установка большей
длины не аллоцирует, `join`/`repeat` бросают `RangeError` при превышении
2^28 байт (как «Invalid string length» в реальных движках).

## Следствия

* test262: 6 929 → **7 290** (46.9 % → 49.4 %); `language/` 41.7 % → 51.8 %.
* Юнит-тестов 478 → 498 (+`tests/js/classes_test.cpp`, +`tests/js/es2015_test.cpp`).
* Два теста пришлось исправить: они читали необъявленные переменные
  (`f1`, `numberToString`) и полагались на прежнее `undefined` — это ровно то
  поведение, которое этап и убрал.
* Утечки: `__proto__`-аксессор держал `shared_ptr` на свой же объект, а
  `Function.prototype.constructor` — на `Function`, которая владеет
  прототипом (циклы `shared_ptr`). Оба цикла убраны: аксессор держит
  `weak_ptr`, а `constructor` отвечается правилом поиска по
  `runtime_.function_prototype`.
* Ограничение: `class` пока без `extends` от встроенных с полной семантикой
  (`class X extends Array` даёт правильную цепочку, но `super()` не
  инициализирует массив), без вычисляемых имён методов и полей классов.
