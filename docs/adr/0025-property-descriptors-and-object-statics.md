# ADR 0025: дескрипторы свойств, `Object.prototype` и честный test262

Дата: 2026-11-05. Этап: 23.

## Контекст

Раннер test262 показывал 20.2 % — цифра оказалась фикцией: вместо
`sta.js`/`assert.js` подставлялась преамбула-заглушка (`assert.throws` бросал
исключение **всегда**, `verifyProperty` был no-op, `sameValue` сравнивал через
`!==`), а любой `includes:` приводил к молчаливому пропуску файла (1651 тест).
Кроме того, в движке не было дескрипторов свойств: `Object` проходил 0.3 %,
хотя это самый базовый встроенный объект.

Нужно было решить три вещи: как считать, что моделью свойств считать и как
связать `Object.prototype` с существующими объектами, не переписывая весь
интерпретатор.

## Решение

### 1. Счёт: сначала честность, потом проценты

Преамбула реализует семантику harness-файлов test262, а не «то, что удобно
движку». Пропуск по `includes:` заменён явным списком поддерживаемых файлов
(`assert.js`, `sta.js`, `propertyHelper.js`, `compareArray.js`,
`isConstructor.js`); неподдерживаемые по-прежнему пропускаются, но отдельным
счётчиком в отчёте. Процент после починки **упал** — это ожидаемо и правильно:
сравнивать новые значения со старыми нельзя, в отчёте они помечены как
«старая, завышенная цифра».

Имя теста, который падает, полезнее имени теста, который «прошёл» на заглушке.

### 2. Модель свойств: атрибуты в `Property`, атрибуты объекта в `Object`

`Property { value, writable, enumerable, configurable }` — плоская структура,
как и раньше, плюс три флага. `Object { extensible, prototype_is_null }`.

Отвергнуто: полноценные `PropertyDescriptor`-объекты с разделением на
data/accessor-описания. Дороже по памяти на каждый объект (а объекты — самое
частое, что создаёт страница), выигрыш только в точности внутренних переходов,
которые тесты не наблюдают.

Accessor-свойства по-прежнему живут в отдельных картах (`getters`/`setters`), а
флаги — в `properties[key]`; значение в `properties` для аксессора игнорируется.
Порядок поиска в `get_member` изменён на «аксессор → данные» (раньше было
наоборот), потому что иначе аксессоры, созданные через `defineProperty`, не
видны.

### 3. `this` в аксессорах: два вида карт

DOM-биндингам `this` не нужен (`getters`/`setters` остались как были), а для
JS-аксессоров добавлены `receiver_getters`/`receiver_setters` с получателем.
Альтернатива — сделать `Getter = std::function<Value(const Value&)>` для всех —
ломает сигнатуры в `bindings.cpp` и заставляет каждый DOM-геттер принимать
неиспользуемый аргумент.

### 4. `Object.prototype` без переписывания создания объектов

Объекты создаются в десятке мест (`make_array`, литералы, `new`, Error,
bindings). Проставлять `prototype` в каждом — широкий и рискованный дифф.
Вместо этого в `Interpreter` появился один `object_prototype`, и
`get_member`/`lookup_property` падают в него, если цепочка закончилась. Это
наблюдаемо эквивалентно наследованию от `Object.prototype` для всех объектов,
у которых нет явного прототипа.

Исключение — `Object.create(null)` и `setPrototypeOf(o, null)`: у таких
объектов стоит `prototype_is_null`, и подстановка не применяется.

### 5. Порядок ключей: детерминированный, но не «порядок вставки»

`properties` — `std::unordered_map`, порядок вставки он не хранит. Ключи
выдаются как «индексы по возрастанию, затем строки по алфавиту». Это
детерминированно (тесты не мигают), но не совпадает со спецификацией.
Переход на упорядоченную карту — отдельная работа (нужен порядок и для
`for-in`, и для `JSON.stringify`), она не окупается на этом этапе.

### 6. `Function::statics`: функции — объекты

Чтобы `f.custom = 1` и `Object.defineProperty(f, …)` работали, у `Function`
появился мешок свойств. `f.prototype.constructor === f` реализовано через
`weak_ptr<Function> owner_function` в прототипе: обычная ссылка создала бы
цикл `function → prototype → function`, который нашему refcount-GC не разорвать.

## Следствия

* test262: 2 692 → **3 600** честно пройденных файлов (18.2 % → 24.4 %),
  `built-ins/Object`: 0.3 % → 18.8 %.
* Юнит-тестов 442 → 453, все зелёные; strict-сборка без предупреждений,
  ASan/UBSan чисто.
* Известные ограничения, зафиксированные в `docs/STAGE-23.md`: strict-режим не
  влияет на запись, порядок ключей не insertion-order, `Array.prototype` и
  `arguments` ещё не существуют, геттеры из `defineProperty` отдаются как
  обёртки (идентичность функции-геттера не сохраняется).
