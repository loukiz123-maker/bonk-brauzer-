# ADR 0006: JavaScript — дерево AST + tree-walking интерпретатор

**Статус:** принято (этап 4) · **Контекст:** нужен исполняемый JS без V8/SpiderMonkey/QuickJS.

## Решение 1: интерпретатор по AST, без байткода

Парсер строит `ast::Expr`/`ast::Stmt` (`src/js/ast.hpp`), интерпретатор обходит дерево
(`src/js/interp.cpp`). Байткод-машина быстрее, но требует: компилятор в инструкции,
регистровое/стековое распределение, отдельный дизассемблер для отладки — и это вторая
точка отказа при том же наборе тестов. Дерево даёт читаемый `--dump` и простую отладку;
скорость не является узким местом, пока страница — это несколько десятков скриптов,
а не бандл на 2 МБ. Переход на байткод возможен позже: AST остаётся неизменным входом.

## Решение 2: значения на `std::shared_ptr`

`js::Value` — тегированное объединение (`Undefined/Null/Boolean/Number/String/Object/Function`),
объекты и функции — `shared_ptr`. Это стандартная библиотека (правило «0 зависимостей»),
никакого unsafe-кода и никакой ручной работы с временем жизни на границе с DOM.
Цена: циклы (`a.self = a`) не собираются — утечка на страницу, которая их создаёт.
Честно задокументировано; tracing GC (mark&sweep по арене) — этап 6.

## Решение 3: accessor-свойства вместо «магических» объектов

Чтобы `el.textContent = 'x'` писал в DOM, а не в JS-обёртку, в `js::Object` добавлены
`getters`/`setters`. Это ~20 строк в интерпретаторе и делает биндинги декларативными:
обёртка один раз описывает, какие свойства читаются/пишутся в `dom::Document`.
Альтернатива — прокси-объекты со специальными видами — потребовала бы отдельной ветки
в `get_member`/`set_member` для каждого DOM-свойства и усложнила бы публичный API.

## Решение 4: идентичность обёрток и отсутствие состояния в DOM

`Bindings` держит `NodeId -> js::Value` таблицу, поэтому `document.body === document.body`
истинно (скрипты сравнивают узлы), а `dom::NodeId` остаётся единственным идентификатором:
устаревший id после удаления узла детектируется, а не превращается в UAF.
Обратный маппинг — через скрытые свойства `__nodeIndex`/`__nodeGeneration` (одно место,
не протекает в DOM).

## Решение 5: скрипты до стилей, повторный layout после событий

`Session::load` исполняет `<script>` сразу после разбора документа — правки DOM попадают
в CSS-каскад и layout того же рендера. `Session::click` после обработчиков пересобирает
layout (дешёвая операция, сотни микросекунд), поэтому `textContent = …` в обработчике
виден на следующем кадре без инкрементальности. Инкрементальная инвалидация
(style/layout dirty sets) — этап 6.

## Последствия

- Нет `class`, `switch`, regex, `eval`, `Promise`, GC — см. таблицу ограничений в
  [`docs/STAGE-04.md`](../STAGE-04.md); все отказы явные (`js.syntax` с текстом причины).
- Публичный API (`bonk/js/js.hpp`) не знает ни о DOM, ни о парсере: его можно тестировать
  отдельно и позже заменить реализацию на байткод без изменения вызывающего кода.
