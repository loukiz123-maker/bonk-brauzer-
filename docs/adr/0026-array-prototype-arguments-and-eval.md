# ADR 0026: `Array.prototype`, объект `arguments`, директный `eval`

Дата: 2026-11-05. Этап: 24.

## Контекст

Методы массива жили прямо в значении массива: `get_member` для `Kind::Array`
возвращал замыкания, захватившие `std::shared_ptr<Object>`. Это работало для
`[1,2].push(3)`, но делало невозможным всё остальное: `[] instanceof Array` было
`false`, `Array.prototype` не существовал, а `Array.prototype.slice.call(arguments)`
— самый частый приём в JavaScript до ES6 — падал.

Объекта `arguments` не было вовсе (`make_array` от фактических аргументов), `eval`
не существовал, а недопустимые цели присваивания (`1 = 2`) обнаруживались только
в рантайме.

## Решение

### 1. Методы — на прототипе, `this` — аргументом

`RuntimeState::array_prototype` — единственный `Array.prototype`; на нём лежат все
методы. Значение массива по-прежнему хранит только `length` и индексы, а
`get_member` при промахе смотрит в `array_prototype`, потом в `Object.prototype`
— ровно как цепочка прототипов, только без явного линка в каждом массиве
(тот же приём, что в ADR 0025 для `Object.prototype`).

Отвергнуто: проставлять `prototype` каждому массиву при создании. Это правка
`make_array`, всех мест создания массивов в bindings и JSON, плюс лишние 8 байт на
каждый массив страницы; выигрыш только в том, что `getPrototypeOf([])` вернул бы
`array_prototype` без спецслучая.

### 2. Методы работают с array-like

Внутри методов `this` разворачивается не в «массив», а в array-like: `length` +
числовые ключи (`array_like_length`/`array_like_get`/`array_like_set`). Это одна
реализация на массивы, `arguments`, DOM-коллекции и строки (`ToObject('abc')` —
array-like из символов), и именно она делает `Array.prototype.slice.call(…)`
работающей.

Для записи в array-like, у которого нет `elements` (например `arguments`),
используется `properties`/`setters`; `length` обновляется свойством.

### 3. `arguments`: связь с параметрами через accessor-колбэки

Спецификация описывает mapped arguments как «отдельные свойства, связанные с
параметрами». Реализация — `getters`/`setters` на индексе: колбэк захватывает
`Scope*` вызова и имя параметра.

Отвергнуто: копировать значения в объект и синхронизировать при каждом обращении
к переменной — пришлось бы править разрешение идентификаторов (самый горячий путь
интерпретатора). Accessor-подход тратит пару `std::function` на параметр и ничего
не стоит на обычных переменных.

Область вызова живёт в арене скоупа до конца программы, поэтому захват сырого
указателя безопасен (это то же допущение, что и у замыканий, ADR 0006).

### 4. `eval`: перехват в `eval_call`, а не «магический» builtin

Natives не знают области вызова, поэтому директный `eval` распознаётся в
`eval_call` (выражение-идентификатор `eval`, чья функция совпадает с глобальной)
и исполняется через `Interpreter::eval_source(source, scope)`. Для косвенных
вызовов глобальный `eval` исполняет текст в глобальной области.

Отвергнуто: передавать «текущую область» в каждый native (лишний параметр во всех
builtin'ах и в `Function::Native` — публичной сигнатуре).

Ограничение: `eval` не различает strict/sloppy (strict нет), `eval` не создаёт
новую область для `let`/`const` (block-scope внутри eval ведёт себя как в sloppy
коде), `eval` не влияет на оптимизации — их нет.

### 5. Ранние ошибки: проверка цели присваивания в парсере

`is_simple_assignment_target` (идентификатор или доступ к свойству) и
`is_assignment_target` (плюс литералы массивов/объектов как паттерны для `=`)
вызываются из `parse_assignment` и из разбора `++`/`--`. Ошибка пишется в
`parser.error` → `js.syntax` → `SyntaxError` в `evaluate()`.

Отвергнуто: отдельный проход «валидация AST» — дороже и не даёт ничего, пока
проверок мало.

## Следствия

* test262: 3 600 → **4 511** (24.4 % → 30.6 %); `Array` 7.7 % → **25.9 %**,
  `language` 35.3 % → **41.7 %**.
* Юнит-тестов 453 → 462; strict-сборка без предупреждений, ASan/UBSan чисто.
* Известные ограничения: строка как array-like копируется (методы, меняющие
  `this`, не пишут обратно в строку — как и должно быть), `arguments` в strict
  должен быть немаппированным (strict-режима нет), `eval` не реализует
  strict-семантику и не изолирует `let`/`const`.
