# ADR 0031: опциональная цепочка через разворачивание постфиксной цепочки, логическое присваивание через одну ссылку

Дата: 2026-11-05. Этап: 29.

## Контекст

К этапу 29 движок умел `??` и `**`, но не знал четырёх возможностей, помеченных в
test262 отдельными `features`: `optional-chaining`, `logical-assignment-operators`,
`numeric-separator-literal`, `coalesce-expression` (последняя — из-за того, что
`??` был, а признак оставался в списке). Файлы с этими признаками не попадали в
запускаемое множество, поэтому 12 562 файла не измерялись вовсе.

Отдельная проблема — семантика присваивания: старая ветка `Assign` считала
правую часть до ссылки и разрешала член выражения дважды (`o.p += 1` вызывал
геттер, потом сеттер, но `a[k()] += 1` вычислял `k()` дважды).

## Решение

### 1. Опциональная цепочка: флаг на узле + разворачивание цепочки

У `ast::Expr` появился `optional`. `a?.b`, `a?.[k]`, `f?.(x)` парсятся как
обычные `Member`/`Call` с этим флагом. Вычисление — `eval_postfix_chain`:

1. постфиксная цепочка разворачивается в вектор шагов (снаружи внутрь), база
   остаётся обычным выражением;
2. база вычисляется один раз;
3. шаги проходятся слева направо: пустой получатель на шаге с `?.` → возврат
   `undefined`, остаток цепочки (включая ключи и аргументы вызовов) не
   вычисляется; пустой получатель на обычном шаге → `TypeError`;
4. получатель запоминается для следующего шага-вызова, поэтому `o?.m()` вызывает
   `m` с `this === o`.

Отвергнуто: сигнальное значение (`ValueType::ShortCircuit`), которое
«протекает» через вычисление. Пришлось бы добавить проверку сигнала в каждый
оператор, вызов и приведение — цена больше, чем один обход цепочки, а забытая
проверка даёт утечку сигнала в пользовательский код.

Отвергнуто: десугаривание в парсере (`a?.b` → `a == null ? void 0 : a.b`).
Выражение `a` тогда вычисляется дважды, а короткое замыкание на всю цепочку
(`a?.b.c.d`) требует временных переменных, которых в AST нет.

Ограничение: цепочка разворачивается только если в ней есть `?.`
(`chain_has_optional`); остальные `Member`/`Call` идут прежним путём, чтобы не
менять поведение и скорость 99 % кода.

### 2. Логическое присваивание: одна ссылка, затем решение

Ветка `Assign` переписана вокруг двух лямбд `read_reference`/`write_reference`:
ссылка (идентификатор или пара «объект + ключ») вычисляется один раз, **до**
правой части; для `||=`/`&&=`/`??=` сначала читается текущее значение и, если
короткое замыкание сработало, возвращается оно — сеттер и правая часть не
вызываются. Обычное `=` теперь тоже вычисляет ссылку до правой части, как в
ES2015 12.14.4.

Отвергнуто: оставить `Assign` как есть и добавить отдельный узел
`LogicalAssign`. Семантика идентична с точностью до «не писать при коротком
замыкании», так что второй узел дублировал бы разбор целей и порядок
вычислений.

### 3. Разделители разрядов — в лексере, не в парсере

`_` отбрасывается при сборке литерала, а `0b`/`0o` добавлены к существующему
`0x`. Парсер по-прежнему получает уже готовое `double`, поэтому ни один
потребитель чисел не изменился.

### 4. Конверт conformance расширен только на реализованное

Из списка неподдерживаемых убраны `coalesce-expression`,
`optional-chaining`, `logical-assignment-operators`,
`numeric-separator-literal`, `exponentiation`. `arrow-function` оставлен:
файлы с этим признаком в test262 почти всегда требуют деструктуризации или
spread, то есть их провал ничего не сказал бы о поддержке стрелок.

Следствие: знаменатель вырос с 14 759 до 15 044 файлов. Проценты между этапами
28 и 29 напрямую несравнимы, поэтому в отчёте этапа фиксируется и прирост
пройденных файлов (+163), и прирост знаменателя (+285).

## Следствия

* test262: 7 290 → **7 453** пройденных файлов (49.4 % → 49.5 % при выросшем
  знаменателе).
* Юнит-тестов 498 → 504 (`tests/js/expressions_test.cpp`).
* Триграф `??=` в C++: любые строковые литералы с этим оператором записываются
  как `"?" "?="`, иначе `-Werror=trigraphs` ломает strict-сборку — ловушка
  зафиксирована и в тестах, и в исходниках.
* Порядок «ссылка → правая часть» в присваивании стал стандартным; это меняет
  наблюдаемое поведение кода, который полагался на прежний порядок (таких мест
  в тестах не оказалось).
