# ADR 0008: процесс на вкладку через fork + pipe и где живёт политика

**Статус**: принято (этап 6).

## Контекст

Этап 6 требует две вещи, которые обычно тянут друг друга в разные стороны:

1. **Изоляция вкладок** — падение рендерера не должно убивать браузер.
2. **Единая политика** — SOP, CORS и CSP должны проверяться в одном месте, иначе
   легко получить «CORS проверен в XHR, но не проверен в подресурсах».

При этом у нас нет ни libuv, ни встроенного event loop: сеть синхронная, скрипты
исполняются в момент разбора документа.

## Решение

1. **`security` — модуль чистых функций, без I/O.** `security::Origin`,
   `check_request`, `check_response`, `CspPolicy` ничего не знают про сокеты и DOM.
   Их можно тестировать таблицей случаев и переиспользовать в `net`, `bindings`
   и `shell` без циклических зависимостей.
2. **Транспорт для скриптов — в `shell`, а не в `bindings`.** `XMLHttpRequest`
   вызывает `NetworkHandler`, который ставит `Session`. Там же: CSP для
   `connect-src`, mixed content, cookies (`net::CookieJar`), сверка CORS-ответа и
   запись в журнал devtools. `bindings` остаётся «переводчиком» JS ↔ объекты.
3. **Изоляция — `fork()` + два pipe, а не общая память.** Родитель пишет
   фиксированный заголовок запроса и полезную нагрузку (target/font/profile),
   ребёнок запускает тот же `Session`, рендерит PNG и отправляет заголовок ответа
   с длинами. Любое расхождение длин = «ответ обрезан» = вкладка считается упавшей.
   `fork()` даёт копию уже загруженных объектов без сериализации состояния, а PNG
   в памяти не требует временных файлов.
4. **Ограничения названы явно.** На платформах без `fork()` `isolation_supported()`
   возвращает `false`; cross-origin запрос, требующий preflight, отклоняется с
   `cors.preflight_required_*` вместо тихой деградации до «simple request».

## Последствия

* «Кросс-доменный запрос без CORS блокируется» и «падение вкладки не убивает
  браузер» проверяются тестами без интернета (локальный сокет-сервер в тесте,
  `simulate_crash` в IPC-запросе).
* Интерактивное окно пока остаётся однопроцессным: у X11-цикла нет отдельного
  процесса рендера, а значит нет и защиты от падения в UI. Это следующий шаг,
  когда появится message loop поверх событий X11.
* `localStorage` стал origin-скоупным (для `file:` — по каталогу), что закрыло
  долг этапа 5; ключ хранилища — FNV-1a от сериализованного origin.
* Синхронный XHR — следствие отсутствия event loop; `fetch`/`Promise` появятся
  вместе с микротасками, и тогда `NetworkHandler` переиспользуется как есть.
