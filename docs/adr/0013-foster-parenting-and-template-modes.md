# ADR 0013: foster parenting — место вставки, а не режим

**Статус**: принято (этап 11).

## Контекст

После этапа 10 в отчёте остались два долга: «порядок foster parenting» (~50
падений корпуса) и «`<template>` не переключает режимы» (29 падений).

Первый долг выглядел как проблема порядка: казалось, что узлы перевешиваются
перед таблицей «не в том порядке». На деле проблема была в другом: мы считали
foster parenting **свойством режима** («в табличных режимах перевешиваем») и
применяли его к любому содержимому, включая то, чья цель — обычный элемент.

Симптом: `<table><div>x</div></table>` давал `<div></div>x`. `<div>` перевешен
правильно, но текст `x` уже вставлен «в таблицу» (с точки зрения режима) и тоже
перевешен, хотя по стандарту его цель — `<div>`.

## Решение

Foster parenting — это часть функции **«appropriate place for inserting a node»**
из стандарта, и включается она по *цели вставки*:

> If foster parenting is enabled and target is a `table`, `tbody`, `tfoot`,
> `thead`, or `tr` element …

Поэтому в парсере появились две функции, через которые проходят **все** вставки
контента:

```cpp
bool foster_target() const;               // текущий узел — табличный контейнер?
void insert_node(dom::NodeId node);       // перевесить или вставить как обычно
void insert_text(std::string_view text);
```

Три следствия:

1. `<table><div>x</div></table>` работает сам собой: `<div>` перевешивается
   (цель — таблица), `x` — нет (цель — `<div>`).
2. Форматирование внутри таблицы идёт через общий `start_formatting()`, поэтому
   `<a>` попадает в активный список и реконструируется на следующем символе.
3. Adoption agency на шаге 16 вставляет узел в common ancestor — теперь через
   `insert_at()`, который перевешивает узел, если common ancestor — табличный
   контейнер.

Отдельно пришлось починить слияние текста: `Document::append_text(parent, …)`
добавляет **ребёнка**, поэтому «дописать в существующий текстовый узел» им
нельзя — текст оказывался вложенным в текстовый узел и пропадал из сериализации
(`<table>A<td>B</td>C</table>` давало `"A"` вместо `"AC"`). Добавлен
`Document::extend_text(node, extra)`.

## Почему не «порядок вставки»

Можно было бы хранить «последний перевешенный узел» и вставлять после него —
именно так иногда реализуют foster parenting. Это работает для текста, но
ломается на элементах: стандарт требует вставлять *непосредственно перед
таблицей* (то есть после всех уже перевешенных узлов), и `insert_before` делает
это без дополнительного состояния. Дополнительное состояние здесь — источник
рассинхронизации при закрытии таблиц.

## Режимы внутри `<template>`

`<template>` — единственное место, где режим не выводится из текущего узла:
содержимое шаблона разбирается «in body», но `<tr>`/`<td>`/`<caption>` внутри
него переключают режим на табличный **без** того, чтобы менять верхний узел
стека. Поэтому добавлен стек `template_modes_` (по записи на шаблон, изначально
`Body`), а `mode()` для шаблона возвращает его верхушку.

Правило сформулировано узко: переключение происходит только когда шаблон сейчас
в режиме `Body`. Без этого условия реализация зацикливалась (рекурсивный
переразбор `<td>`), что и было поймано ASan-прогоном: stack overflow.

## Следствия

1. Все вставки контента идут через `insert_node`/`insert_text`; прямые
   `append_child` остались только там, где стандарт говорит «append to X»
   (например, копия formatting-элемента внутрь furthest block).
2. Текстовые узлы теперь могут дописываться (`extend_text`), а не только
   создаваться — это нужно и foster parenting, и будущему `textContent`.
3. Остаточная неточность: «in template» обрабатывает только стартовые теги
   табличной группы; остальные группы токенов внутри шаблона идут по общим
   правилам. В отчёте это 28 оставшихся падений `template.dat`.
