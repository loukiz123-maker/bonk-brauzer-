# ADR 0012: режим вставки выводится из стека, а не хранится флагом

**Статус**: принято (этап 10).

## Контекст

До этого этапа парсер был одним циклом «in body» с заплатками для таблиц:

```cpp
if ((name == "td" || name == "th" || name == "tr" || ...) && nearest_table().valid()) {
  // снять стек «до табличного контекста», вставить неявные tbody/tr
}
if (table_context() && !contains(kTableAllowed, name)) { /* foster parenting */ }
```

Заплатки покрывали `<table><tr><td>` и разваливались на `<caption>`,
`<colgroup>`, ячейках без `</td>`, вложенных таблицах, тексте между `</tr>` и
`</table>`. Каждая новая табличная конструкция требовала ещё одной ветки `if`, а
ветки начинали конфликтовать друг с другом.

По стандарту это **insertion modes**: правила выбираются по текущему узлу стека
(«in table», «in table body», «in row», «in cell», «in column group», «in body») и
оформлены как «process the token using the rules for the X insertion mode».

Были три варианта реализации:

1. продолжать добавлять заплатки;
2. полный автомат: поле `mode_`, стек режимов (`template` его требует), явные
   переходы;
3. выводить режим из стека: `mode()` смотрит на текущий узел, обработчики
   возвращают «токен забран» и проваливаются дальше.

## Решение

Вариант 3.

* Для шести наших режимов «текущий узел» и есть режим: `table` → Table,
  `tbody/thead/tfoot` → TableBody, `tr` → Row, `td/th` → Cell, `colgroup` →
  ColumnGroup. Рассинхронизировать режим и стек невозможно — состояние одно.
* Переразбор («reprocess the token») — прямой рекурсивный вызов обработчика
  после изменения стека. Это буквально то, что делает стандарт, и это дешевле
  очереди отложенных токенов.
* Каскад режимов (`TableBody` → `Table`, `Row` → `TableBody` → `Table`)
  реализован возвратом `bool`: `false` означает «токен не мой, применяй правила
  следующего режима».

## Почему не полный автомат

Полный автомат нужен там, где режим **не** определяется текущим узлом: «in
template» переключается на «in table body» при `<tr>`, «after head» — на «in
body» по любому другому тегу. У нас пока нет ни `<template>`-переключений, ни
раздельных «before head»/«after head» как состояний (они выражены ленивым
созданием `head_`/`body_`). Вводить поле `mode_` и стек режимов сейчас — значит
поддерживать второе состояние, которое почти всегда совпадает с первым.

Когда появится «in template» с переключениями, режим придётся хранить; тогда
`mode()` станет «взять верхний режим из стека, если он есть, иначе вывести из
узла». Это локальное изменение одной функции, а не переписывание парсера.

## Следствия

1. Табличные заплатки удалены: `kTableAllowed`, блок «table fixes» и
   `template_above_table()` больше не существуют. `<template>` внутри таблицы
   даёт режим `Body` естественным образом.
2. Foster parenting стал единственным способом «вынести лишнее из таблицы», и он
   применяется в трёх режимах (`Table`, `TableBody`, `Row`).
3. Символы внутри табличных режимов обрабатываются отдельно: пробельные остаются
   в таблице, остальные перевешиваются. Раньше это решалось в `append_text`.
4. Появились вспомогательные «clear the stack back to X context» операции
   (`clear_to_table_context`, `clear_to_table_body_context`, `clear_to_row_context`,
   `pop_through`) — они же используются при закрытии ячейки/строки/секции.
5. Остаточная неточность: порядок foster parenting и слияние текстовых узлов
   перед таблицей реализованы приближённо (~50 оставшихся падений корпуса).
   Это следующий кандидат на исправление — уже внутри новой схемы.
