# Направление: отдельная Android VM для Linux

Это план, не работающий эмулятор. Waydroid и Linux-контейнер для этого пути
не используются. BlueStacks — закрытый продукт, мы не знаем всех деталей его
реализации и не копируем его код. Похожий архитектурный принцип — запуск
Android внутри аппаратно ускоренной виртуальной машины с отдельной оболочкой.
[BlueStacks](https://support.bluestacks.com/hc/en-us/articles/4412148150157-Solution-for-when-BlueStacks-5-is-unable-to-launch-when-Hyper-V-is-enabled)
описывает использование виртуализации и Hyper-V в Windows; на Linux общим
механизмом ускорения является [KVM](https://developer.android.com/studio/run/emulator-acceleration).
Это не делает Linux-движок идентичным BlueStacks.

## Проверка готовности хоста

После установки проекта (`pip install -e .`) обычным пользователем:

```bash
python -m lynxdroid.doctor.vm_probe
python -m lynxdroid.doctor.vm_probe --json
```

Проверка открывает `/dev/kvm` и запрашивает версию API, не создавая виртуальную
машину и не меняя настройки. Статус `available` означает только, что текущий
процесс получил ответ от KVM; он не подтверждает загрузку Android, работу GPU,
запуск игр, производительность или права на другие устройства. При отсутствии
устройства или прав выводится соответствующий статус; исправление настроек
остаётся отдельным решением пользователя. CPU-флаг — лишь подсказка.

## Проверка создания пустой VM

После обычной проверки KVM по явному решению пользователя можно выполнить:

```bash
python -m lynxdroid.backend.kvm_smoke --confirm
```

Команда создаёт временную пустую VM, один vCPU и его run-mapping, затем
закрывает их, в том числе при ошибках. Никакой код гостя и Android не
запускаются; сеть, диск, файлы и настройки системы не изменяются. Результат
успеха означает только, что данные операции KVM выполнены. Это ещё не VM
менеджер и не оценка работоспособности Android. Без `--confirm` действий нет.
Автоматические тесты используют поддельные системные операции; проверка на
реальном Linux с доступным KVM ещё необходима.

## Эксперимент: выполнение тестовой программы в KVM

В **исходном репозитории**, на x86_64 Linux с компилятором C и KVM headers:

```bash
cc -std=c11 -O2 -Wall -Wextra -Werror runtime/kvm_hello.c -o /tmp/lynxdroid-kvm-hello
/tmp/lynxdroid-kvm-hello --confirm
```

По явному подтверждению программа создаёт временную пустую VM, 64 КиБ памяти
и один виртуальный процессор. Встроенная тестовая программа передаёт по
виртуальному отладочному порту `OK` и символ `U` в ограниченный прототип
последовательного порта COM1, затем выполняет `HLT`. Проверяются ожидаемые
I/O события и `KVM_EXIT_HLT`. Порт поддерживает только небольшой polling-набор
регистров, без прерываний, FIFO и ввода с хоста; он не проверен с Linux или
Android и не является полноценным 16550. Образов, пользовательского кода, дисков, сети и
Android в этой VM нет. VM и её ресурсы закрываются при выходе; сетевые
правила и настройки хоста не меняются. Сигнал ограничивает ожидание KVM_RUN
пятью секундами, но не гарантирует прерывание неисправного ядра. Не запускайте
с sudo: используйте обычные разрешения на `/dev/kvm`.

Это минимальный исполняемый эксперимент, **не Android runtime** и не проверка
игр. В текущей среде `/dev/kvm` отсутствует; компиляция проверена, но реальное
выполнение гостя здесь не подтверждено. `pytest` компилирует эксперимент и
проверяет отказ без подтверждения; реальную проверку можно явно включить на
своём x86_64 Linux командой `LYNX_KVM_SMOKE=1 pytest tests/backend/test_kvm_hello.py`.

## Память гостя

`runtime/guest_memory.h` добавляет ограниченные чтение и запись в один непрерывный
участок гостевой RAM. Границы проверяются без переполнения адреса; операции не
выходят за буфер, перекрывающиеся участки обрабатываются корректно. KVM-демо
записывает свой встроенный код через этот интерфейс. Проверки выполняются на
синтетических буферах без KVM. Это ещё не менеджер нескольких областей, MMIO,
защита памяти или загрузчик ядра, а также не демонстрация загрузки Android.

## Подготовка x86 Linux-ядра в памяти

`runtime/x86_linux_stage.h` содержит отдельную экспериментальную процедуру
для ограниченного набора x86_64 bzImage с Linux boot protocol 2.12 и новее.
Она проверяет сигнатуру, версию, загрузочные флаги и размеры, затем копирует
setup и защищённую часть в заранее выделенную гостевую память по обычным
адресам `0x10000` и `0x100000`. До записи проверяются диапазоны, требуемое
место для инициализации и отсутствие наложения исходного файла на RAM.
Тест использует только синтетические данные и не запускает ядро. Инспекция
не проверяет подпись, подлинность, все ограничения загрузки или совместимость
конкретного Android-образа.

Это не загрузчик: boot_params, E820, регистры vCPU, прерывания, виртуальные
устройства и всё окружение Android отсутствуют. Функция не подключена к
KVM-демо или лаунчеру. Linux guest boot, тестовый APK и Android input по-прежнему
не проводились и требуют отдельного отчёта при интеграции.

## Проверка заголовка выбранного образа

```bash
python -m lynxdroid.backend.vm_image /path/to/boot.img
```

Это офлайн-инспектор только обычного Android boot header v3/v4, по
[документации AOSP](https://source.android.com/docs/core/architecture/bootloader/boot-image-header).
Он проверяет магическое число, размер заголовка и границы заявленных компонентов;
символические ссылки и не обычные файлы отклоняются. v0–v2, vendor_boot,
архивы, образы дисков, другие форматы и чтение внутри Android SDK не реализованы.
Наличие корректного заголовка **не подтверждает** архитектуру, подлинность,
целостность, совместимость с VM или право распространять образ. Команда не
скачивает, не запускает и не изменяет файлы. Для запуска Android необходимы и
другие компоненты, зависящие от выбранной сборки.

## Архитектура и этапы

1. **Контракт runtime и безопасность.** Вынести отдельный VM backend без
   вызовов Waydroid; контролировать жизненный цикл изолированного процесса,
   безопасное завершение, приватные сокеты и каталоги образов. Определить
   модель разрешений и обновлений, не требовать постоянного root на хосте.
2. **Первый boot.** Выбрать и лицензировать совместимый Android guest image,
   архитектуру x86_64, ядро, bootloader и необходимые виртуальные устройства.
   KVM — только интерфейс ускорения, а не законченный эмулятор: нужен VMM,
   поддержка виртуальных устройств и boot chain. Собственный VMM — большой
   отдельный проект; использование внешней базы потребует отдельного решения
   об архитектуре, лицензиях и зависимости. Доказательство: boot_completed и
   запуск собственного тестового APK на целевом Linux.
3. **Изображение и ввод.** Определить графический стек гостя и хоста, канал
   вывода кадра в центр лаунчера, масштаб и задержку; реализовать безопасный
   ввод и проверенные многопальцевые события. Никакой передачи от текущего
   офлайн-редактора в Android сейчас нет. Для 3D нужна реальная проверка GPU;
   [AOSP](https://source.android.com/docs/devices/cuttlefish/gpu) различает
   GPU-ускорение и медленнее работающий программный рендеринг.
4. **Приложения и совместимость.** Реализовать установку и состояние APK,
   звук, сеть, профиль на идентификатор приложения и надёжное определение
   активного приложения. Проверять каждый ABI: x86_64 гостя не гарантирует
   запуск ARM-only библиотек; совместимая трансляция — отдельная задача с
   ограничениями лицензий и производительности. Google Play и сертификация не
   являются автоматической частью AOSP и должны иметь законную основу.
5. **Тесты и измерения.** Тесты загрузки, сбоев, закрытия и сохранности данных,
   одновременного ввода, FPS, задержки, температуры и загрузки CPU/GPU на
   целевом ПК. Установить честные границы совместимости и поддерживаемых игр.

## Standoff 2

Запуск игры и её системные проверки не подтверждены. Правила игры могут
ограничивать вход на root-устройствах, а разработчик не обещает поддержку
эмуляторов: см. [аудит](ANDROID_RUNTIME_REVIEW_RU.md). Даже если KVM и Android
VM заработают, совместимость игры и риск для аккаунта останутся отдельными
вопросами. Не подменять результаты integrity или anti-cheat проверок.
