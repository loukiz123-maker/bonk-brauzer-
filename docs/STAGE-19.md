# Этап 19: последние состояния токенайзера и пространства имён в API

Этап 18 довёл дерево html5lib до 100 %, но список пропусков токенайзера
оставался длинным: 113 случаев, из которых 56 — «неизвестное начальное
состояние», а 54 — таблица «задокументированных расхождений». Оказалось, что
это разные истории: 56 — это CDATA-секция, которую токенайзер умел включать
только из `markup declaration open`; 54 — это (в основном) устаревшая модель
processing instruction, причём половина из них на самом деле уже проходила и
скрывалась слишком широкой подстрокой в таблице. Здесь закрыто и то, и другое,
плюс сделан следующий логичный шаг после этапа 18: пространства имён дошли до
DOM API и селекторов — иначе `<svg>`/`<foreignObject>` для `querySelector` и
`getElementsByTagName` оставались элементами с «неправильным» регистром.

Пропусков токенайзера было 113 (56 состояний + 3 PI + 54 «расхождения»), стало
28 — и все 28 об одном: html5lib-модель processing instruction. Счётчика
«skipped (unknown initial state)» больше нет: все шесть начальных состояний
корпуса поддерживаются.

## Что сделано

### 1. CDATA section state как начальное состояние

Корпус умеет стартовать токенайзер в шести состояниях (`initialStates`), и
шестое — `CDATA section state` — было единственным неподдержанным: в движке это
состояние включалось только из `markup declaration open`, да и то лишь внутри
внешнего контента. Появился `Tokenizer::enter_cdata_section()` — ровно то же
состояние, что и у tree builder'а, просто выставленное снаружи. 56 случаев
пошли в прогон и прошли, включая ветку со скобками: `]]]>` закрывает секцию
после одного `]`, а незакрытая секция доходит до EOF.

### 2. Таблица «известных расхождений» удалена

Было: `kKnownDivergences` — список пар (файл, подстрока описания), которые
пропускались как «известное расхождение». Две проблемы:

* подстрока `<?` в `test3.test` накрывала и те случаи, где корпус уже ждёт
  **комментарий** (`<?!` → `Comment "?!"`) — то есть 24 случая пропускались,
  хотя проходили;
* четыре записи про U+0000 («спек даёт U+FFFD») были просто неверны: в data
  state спек как раз **сохраняет** NUL, и наш токенайзер так и делает с этапа 1.

Теперь пропуск определяется по форме ожидания, а не по списку описаний:

* ввод начинается с `<?`, а ожидаемый вывод **пуст** — 25 случаев: html5lib
  считает `<?…` processing instruction'ом и на EOF его выбрасывает
  (`eof-in-processing-instruction`);
* в ожидаемом выводе есть токен `ProcessingInstruction` — 3 случая: такого
  типа токена в стандарте нет.

Оба условия «самоисцеляющиеся»: если корпус переедет на комментарии (как уже
сделал для 24 случаев), те же самые случаи пойдут в прогон и пройдут. Сверено с
актуальным upstream: `tokenizer/test3.test` из `html5lib-tests@master`
байт-в-байт совпадает с нашим снимком, то есть это не устаревшая копия, а
действующая позиция корпуса. Поведение спека зафиксировано юнит-тестом
`tokenizer.unexpected_question_mark_is_a_bogus_comment`: `<?xml version=1?>`
даёт `Comment("?xml version=1?")`.

### 3. `getElementsByTagName`: регистр зависит от пространства имён

До этапа сравнение было побайтовым, и `<svg>` был «особым» элементом с
необъяснимым поведением. По DOM-стандарту в HTML-документе имя HTML-элемента
сравнивается без учёта регистра, а иностранного — точно:

* `getElementsByTagName("DIV")` находит `<div>`;
* `getElementsByTagName("foreignobject")` **не** находит `<foreignObject>`
  (парсер привёл имя к camelCase, и это его настоящее имя);
* `getElementsByTagName("*")` возвращает всё, включая SVG/MathML.

### 4. Селекторы: тип-селектор больше не приводится к нижнему регистру

`parse_selector_list("foreignObject")` раньше сохранял `foreignobject`, поэтому
селектор не мог совпасть ни с чем: `querySelector("foreignObject")` возвращал
`null`, а правило CSS `foreignObject { … }` не применялось никогда. Теперь
разбор сохраняет написание, а сравнение учитывает пространство имён элемента:

* HTML-элементы — ASCII case-insensitive (`DIV` и `div` — одно и то же,
  `SPAN` внутри `<foreignObject>` тоже матчится);
* иностранные — точное совпадение (`foreignObject`, `linearGradient`,
  `feBlend`), как и требует CSS Selectors для не-HTML-элементов.

Так как CSS-каскад использует тот же движок селекторов, правило
`foreignObject { color: … }` заработало без отдельной правки в `css`.

* `make MODE=release WARN="… -Werror"` — 0 предупреждений;
* `make MODE=debug SAN=address,undefined` + `bonk_tests` + tree/tokenizer

  рисуется без падений (внешний контент пока раскладывается как обычные боксы).
