# Этап 18: внешний контент — пространства имён SVG и MathML

Этап 17 оставил ровно один блок дерева html5lib «вне конверта»: 236 случаев, в
которых в дереве появлялся `<svg>` или `<math>`. Причина была не в правилах
разбора, а в модели данных: у DOM не было пространств имён, поэтому `<svg svg>`
и `<svg g>` были неотличимы от HTML-элементов `svg` и `g`, а интеграционные
точки (`foreignObject`, `mi`, `annotationText`…) вообще не на что было
опереть. Здесь это закрыто: в DOM появились пространства имён и префиксы
атрибутов, в tree builder — правила «in foreign content», диспетчер tree
construction, breakout-теги, интеграционные точки и CDATA-секции. Корпус
дерева идёт **целиком**, без единого исключения.

## Что сделано

### 1. Пространства имён в DOM

`dom::Namespace { Html, Svg, Mathml }` — поле у узла-элемента, а не отдельный
тип узла: `create_element(name, ns)`, `element_namespace(id)`,
`namespace_name(ns)`. У атрибута появился префикс (`Attribute::prefix`,
`AttrRecord::prefix`), потому что `xlink:href` — это не атрибут с именем
`xlink:href`, а атрибут `href` в пространстве XLink с префиксом `xlink`.

Два следствия, которые пришлось развести явно:

* `set_attribute(id, name, value)` по-прежнему пишет «обычный» атрибут и
  сравнивает только имена без префикса: `has_attribute(el, "href")` не должен
  срабатывать на `xlink:href`;
* `attribute_ns(id, prefix, name)` — отдельный доступ к префиксным атрибутам,
  им пользуются сериализатор и тесты.

Сериализатор (`to_html`) пишет префикс обратно через двоеточие
(`xlink:href="…"`), а отладочный дамп и раннер дерева — в форме html5lib:
`<svg font>`, `<math mi>`, `xlink href="…"`.

### 2. Tree builder: «in foreign content»

Диспетчер (`use_foreign_rules`) — первое, что видит каждый токен:

* текущий узел HTML-элемент → обычные режимы вставки;
* MathML text integration point (`mi`, `mo`, `mn`, `ms`, `mtext`) → HTML-правила
  для всего, кроме `<mglyph>`/`<malignmark>` и для символьных токенов;
* HTML integration point (`annotation-xml` с `encoding=text/html` или
  `application/xhtml+xml`, SVG `foreignObject`/`desc`/`title`) → HTML-правила для
  start tag и символов;
* `<svg>` внутри `annotation-xml` → снова SVG;
* EOF → обычные правила;
* иначе — «in foreign content».

Само «in foreign content»:

* **breakout-теги**: список из 44 стартовых тегов (`b`, `div`, `p`, `table`,
  `span`, …) плюс `font` только с `color`/`face`/`size`, плюс `</br>`/`</p>` —
  стек сбрасывается до ближайшего HTML-элемента или интеграционной точки, токен
  переразбирается по HTML-правилам;
* **case-adjust**: 37 имён SVG (`altglyph` → `altGlyph`, `foreignobject` →
  `foreignObject`, `feblend` → `feBlend`, …) и 58 имён SVG-атрибутов
  (`viewbox` → `viewBox`, `attributename` → `attributeName`, …); у MathML
  ровно одно — `definitionurl` → `definitionURL`;
* **имена с префиксом**: `xlink:actuate|arcrole|href|role|show|title|type`,
  `xml:lang`, `xml:space`, `xmlns` и `xmlns:xlink` — из таблицы стандарта; всё
  остальное с двоеточием (например `xml:base`) остаётся литеральным именем
  атрибута, как и требует html5lib;
* **концы тегов**: `</script>` в SVG закрывает скрипт, любой другой ищет
  совпадение по имени (без учёта регистра) вверх по стеку и, добравшись до
  HTML-элемента, переразбирается по HTML-правилам.

Одна тонкость, на которой легко зациклиться: «переразобрать токен по HTML-
правилам» не должно снова проходить через диспетчер. Иначе `</br>` в `<mtext>`
уходит в бесконечную рекурсию (pop ничего не делает — текущий узел и есть
интеграционная точка). Поэтому HTML-сторона вынесена в `handle_start_tag` /
`handle_end_tag_name`, а диспетчер входа — в `process_start_tag` /
`process_end_tag`; «reprocess in HTML content» вызывает HTML-функции напрямую.

### 3. Проверки области видимости и «шаблонности» стали namespace-aware

`<svg td>` — не ячейка таблицы, `<svg template>` — не шаблон, `<svg p>` — не
абзац, `<svg font>` — не `<font>`. Все обходы стека, которые сравнивают имя
(`has_open`, `close_open`, `pop_through`, `tag_in_scope`, `in_table_scope`,
`p_in_scope`, `mode()`, `generate_implied_end_tags`, обработка `</template>` и
`</td>`), теперь требуют HTML-элемента (`is_html_named`). Без этого
`<table><tr><td><svg><td></td></svg></td>Foo` теряет foster-parenting: `</td>`
«находил» SVG-элемент с именем `td` и закрывал вложенное поддерево.

То же и в обратную сторону: интеграционные точки стали границами области
видимости (`is_scope_boundary`), поэтому `<p><svg><title><p>` оставляет
второй абзац внутри `<title>`, а не закрывает внешний `<p>`.

Попутно всплыл настоящий (не связанный с SVG) пробел: «in caption» в парсере
был «схлопнут» в in body, и `</table>` внутри `<caption><p>` не закрывал
таблицу. Теперь `caption_context()` перехватывает table-структурные токены:
они закрывают caption и переразбираются на уровень выше
(`<table><caption><p>x</table><p>y` даёт два соседних абзаца и закрытую
таблицу).

### 4. CDATA и фрагменты

`<![CDATA[…]]>` — символьные данные во внешнем контенте и bogus comment в
HTML. Токенайзер не знает про дерево, поэтому tree builder перед каждым
`next()` сообщает ему `set_foreign_content(current_namespace() != Html)` — это
и есть «adjusted current node» стандарта.

Фрагменты: `parse_fragment(bytes, "svg path")` / `"math ms"` — так контекст
записан в корпусе; второй элемент строки — имя тега, первый — его
пространство. Контекст-элемент с иностранным пространством **не** включает
RCDATA даже для `title`: `<svg title>` — обычный иностранный элемент, разметка
внутри него остаётся разметкой.

### 5. Мелочи, которые всплыли по дороге

* `frameset-ok` не сбрасывается на NUL и пробелах во внешнем контенте
  (`<svg>\0</svg><frameset>` всё ещё создаёт frameset);
* `<template>` и `<svg>`/`<math>` не включают текстовые состояния токенайзера,
  если элемент иностранный: `<svg><title><p>` — это разметка, а не текст;
* `solidcolor` → `solidColor` из таблицы убран: в стандарте он закомментирован,
  и корпус ожидает имя без изменений;
* `to_html`/дамп печатают пространство имён перед именем — формат html5lib.
