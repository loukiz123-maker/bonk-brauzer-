# Этап 10: insertion modes вместо заплаток вокруг таблиц

К этапу 9 у парсера был один большой цикл «in body» и несколько заплаток для
таблиц: «если сверху таблица или tbody — сделать неявный `<tbody>/<tr>`»,
«если элемент не в списке разрешённых — перевесить перед таблицей». Заплатки
работали для простых таблиц и разваливались на всём остальном: `<caption>`,
`<colgroup>`, ячейки без `</td>`, вложенные таблицы, текст между `</tr>` и
`</table>`.

По стандарту это не заплатки, а **режимы вставки**: текущий узел стека
определяет, какой набор правил применяется. На этом этапе движок переведён на
такую схему.

Прирост скромнее, чем на этапах 8–9, и это ожидаемо: режимы вставки почти не
добавляют «новых зелёных галочек» на простых документах — они убирают *класс*
ошибок и делают поведение предсказуемым. Часть выигрыша съели честные
компромиссы (см. ниже), полтора десятка случаев ушли в «правильно, но всё равно
не совпадает» из-за отсутствующих соседних правил.

## Что сделано

### 1. Режим выводится из стека, а не хранится флагом

```cpp
enum class Mode { Body, Table, TableBody, Row, Cell, ColumnGroup };

[[nodiscard]] Mode mode() const {
  const std::string_view top = tag_of(stack_.back());
  if (top == "table")   return Mode::Table;
  if (top == "tbody" || top == "thead" || top == "tfoot") return Mode::TableBody;
  if (top == "tr")      return Mode::Row;
  if (top == "td" || top == "th") return Mode::Cell;
  if (top == "colgroup") return Mode::ColumnGroup;
  return Mode::Body;
}
```

Отдельной переменной-состояния нет: для этих шести режимов текущий узел и есть
режим, а значит рассинхронизировать их невозможно. `<template>` естественным
образом даёт `Body` (шаблон — не таблица), и старое правило
`template_above_table()` больше не нужно.

### 2. Правила по режимам

| режим | что делает |
|---|---|
| `Table` | `<caption>`/`<colgroup>`/`<col>`/`<tbody>`/`<tfoot>`/`<thead>` — вставляются; `<td>`/`<th>`/`<tr>` — с неявными `<tbody>`/`<tr>`; вложенный `<table>` закрывает внешнюю таблицу и переразбирается; `<input type=hidden>` и `<form>` живут внутри таблицы; всё остальное **перевешивается перед таблицей** (foster parenting) |
| `TableBody` | `<tr>` — вставляется; `<td>`/`<th>` — с неявным `<tr>`; `<caption>`/`<col>`/`<colgroup>`/`<tbody>` — закрывают секцию и переразбираются |
| `Row` | `<td>`/`<th>` — открывают ячейку (плюс маркер в списке форматирования); `<tr>`/`<tbody>`/`<caption>` — закрывают строку и переразбираются |
| `Cell` | `<td>`/`<th>`/`<tr>`/`<tbody>`/`<table>` — закрывают ячейку и переразбираются; остальное — обычные правила `<body>` |
| `ColumnGroup` | `<col>` — void; остальное закрывает `<colgroup>` и переразбирается |
| `Body` | прежний поток: `implied end tags`, formatting-элементы и adoption agency |

Каждый обработчик возвращает «я забрал токен»; если нет, токен проваливается в
правила следующего режима — ровно как в стандарте («process the token using the
rules for the X insertion mode»). Переразбор сделан прямым рекурсивным вызовом
`handle_start_tag`/`handle_end_tag_name` после изменения стека.

### 3. Мелкие правила, без которых режимы бесполезны

* `</p>` и прочие закрывающие теги **до** `<body>` игнорируются (режимы «before
  head»/«after head»): раньше `</p>` на пустом месте создавал абзац;
* комментарий после `</html>` у frameset-документа уходит в документ, а не в
  `<html>`; пробелы после `</frameset>` — в `<html>`, остальной текст
  отбрасывается; стартовые теги после `</frameset>` игнорируются, кроме
  `html`/`noframes`/`template`;
* раннер tree-construction печатает комментарии так же, как html5lib: одной
  строкой, с переносами внутри (`--!` + перевод строки больше не даёт
  расхождения на пустом месте).

## Что работает

* `<table><td>x` → `<table><tbody><tr><td>x</td></tr></tbody></table>`;
* `<table>x<td>y` → текст перевешен перед таблицей, ячейка на месте;
* `<table><div>x</div></table>` → `<div>` перед таблицей;
* `<table><caption>c</caption><tr><td>x` → caption, затем неявные tbody/tr;
* ячейки закрывают друг друга без `</td>`;
* `<table><tr><td><b>a</b></table>` — formatting-элемент закрывается вместе с
  ячейкой;
* демо: [`docs/demo/table.html`](demo/table.html) →
  [`docs/demo/table.png`](demo/table.png).

## Что не работает (и почему)

Оставшиеся 270 падений tree-construction:

| кластер | случаев | причина |
|---|---|---|
| foster parenting в сложных комбинациях | ~50 | порядок перевешивания и слияние текстовых узлов перед таблицей; у нас «вставить перед таблицей», у стандарта — «в appropriate place for inserting a node» с учётом уже перевешенных |
| `<template>` + таблица | 29 | режим «in template» должен переключаться на «in table body»/«in row»; у нас шаблон всегда даёт `Body` |
| `noscript` | 19 | нужен флаг scripting (сейчас всегда «scripting off») |
| `tests1/3/7/19` | ~60 | «in body» правила, которых у нас нет списком: `<h1>` в `<h1>`, `<menuitem>`, `</br>`, порядок в `<select>` |
| `plain-text-unsafe.dat` | 15 | `plaintext`, CR/NUL-нормализация |
| остальное | ~100 | DOCTYPE-идентификаторы, комментарии `--!`, `<rb>` внутри `<p>` |

Вне конверта по-прежнему 412 случаев: fragment parsing и внешний контент
SVG/MathML. Также нет: рендеринга frameset'ов, `template.content` в JS,
абсолютного позиционирования, `border-collapse`, Date/RegExp/Map/Set/Promise,
классов и генераторов в JS.

## Решение

[ADR 0012](adr/0012-insertion-modes.md): режим вставки выводится из текущего
узла стека, а не хранится отдельным полем; обработчики режимов возвращают «токен
забран» и проваливаются дальше по цепочке. Это дешевле полноценного автомата
состояний (нет отдельного стека режимов) и на наших шести режимах эквивалентно
стандарту.
